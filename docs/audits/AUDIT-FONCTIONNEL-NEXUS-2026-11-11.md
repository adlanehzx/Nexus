# Audit fonctionnel de Nexus — 11 novembre 2026

## 1. Verdict et périmètre

**Nexus est une alpha personnelle substantielle, mais pas encore une solution complète distribuable au grand public.** Les briques d'exécution, de persistance, de permissions et de supervision sont réelles. Leur assemblage reste inégal : arrêter le suivi n'annule pas une mission, les confirmations générales ne sont pas raccordées au chat web, plusieurs bibliothèques d'intégration n'alimentent pas le registre des outils, et une soumission carrière peut être seulement enregistrée. Des garanties de sécurité doivent être corrigées avant d'élargir l'accès.

Le principal investissement doit porter sur un parcours personnel continu et récupérable, puis sur l'exploitation et l'isolation. Cadran apporte une structure et une lisibilité utiles ; il ne corrige pas à lui seul les lacunes du moteur, du contrôle d'accès ou des sauvegardes. Le plan associé est [PLAN-AMELIORATION-NEXUS-2026-11-11.md](PLAN-AMELIORATION-NEXUS-2026-11-11.md).

Aucun changement applicatif, migration, installation, reset, stash, checkout, commit ou push dans ce dépôt. Les tests Git utilisent leurs répertoires temporaires, pas le dépôt Nexus.

Cette revue couvre tous les domaines et toutes les familles de composants inventoriés, par traçage ciblé des sources, routes, interfaces et tests. **Elle n'est ni une lecture exhaustive de chaque ligne ni une validation en production de chaque fonction.** Une capacité non essayée avec son matériel, son fournisseur ou sa base réelle reste non vérifiée, même si ses tests locaux passent. ### Échelle des statuts

| Statut                       | Signification dans ce rapport                                                                                                                   |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fonctionnel vérifié (FV)** | Comportement effectivement exécuté dans les conditions décrites, généralement test local ou fixture. Ne vaut pas certification de bout en bout. |
| **Partiel (P)**              | Mécanisme réel identifié, mais chaîne incomplète, frontière défaillante ou dépendance importante non validée.                                   |
| **Simulé (S)**               | Le résultat représente volontairement un enregistrement, un double de test ou une exécution virtuelle ; il ne prouve pas l'effet externe.       |
| **Absent (A)**               | Capacité précise non trouvée dans les surfaces et implémentations inspectées. L'absence est bornée à ce périmètre.                              |
| **Non vérifié (NV)**         | Présence possible ou code présent, sans preuve suffisante de fonctionnement effectif ici.                                                       |

Les sous-capacités sont séparées : « FV en test » et « NV en réel » peuvent coexister. Priorités : **P0** bloque la confiance ou l'ouverture du périmètre concerné ; **P1** nécessaire au produit utilisable ; **P2** amélioration ou extension après le socle. Une P0 conditionnelle à l'usage multi-utilisateur n'est pas une affirmation de compromission d'une installation personnelle.

## 4. Constats priorisés

### F01 — P0 : une isolation MCP demandée peut disparaître silencieusement

**Reproduit sans démarrer de serveur MCP.** `packages/mcp/src/sandbox.ts:188` renvoie la commande originale lorsque bwrap est absent (`:190–195`). `packages/mcp/src/client.ts:277` exploite la préparation du transport. Précondition : serveur stdio configuré avec bwrap, hôte sans capacité disponible. Impact : droits de l'utilisateur hôte au lieu de l'isolation attendue. Le test synthétique de cette session renvoie bien `node`.

Correction attendue : refus explicite si l'isolation demandée n'est pas disponible ; un éventuel mode non isolé doit être un choix séparé, visible, réservé aux extensions de confiance. Recette négative sur hôte sans bwrap et sur namespace refusé. Un test d'arguments « hardened » passant n'annule pas ce défaut.

### F02 — P0 : racine lisible dans la sandbox MCP

**Constat statique.** `packages/mcp/src/sandbox.ts:201` monte `/` en lecture seule, ou en écriture selon l'option. La lecture seule protège certaines écritures, pas les fichiers confidentiels lisibles par le compte. L'absence de réseau ne protège pas le canal de sortie MCP. Aucun vrai secret n'a été lu. Fournir un root minimal, un HOME dédié et des montages explicites ; tester avec un faux fichier confidentiel temporaire.

### F03 — P0 : consommation non atomique du refresh token

**Reproduit : deux refresh concurrents réussissent sur deux.** `services/api/src/services/auth-service.ts:156` sépare lecture, contrôle, révocation et ouverture de session ; `services/api/src/services/persistence/prisma-session-store.ts:37` révoque sans condition de consommation unique. Reproduction sur store mémoire seulement ; structure SQL relue, concurrence PostgreSQL non exercée. Il faut une consommation conditionnelle et création du successeur atomiques, un seul gagnant et une politique de rejeu testée sans déconnecter arbitrairement les clients légitimes.

### F04 — P0 avant multi-utilisateur : checkpoints sans propriété ni racine autorisée

**Traçage statique API → manager.** Les routes sont montées dans `services/api/src/app.ts:332`. Le guard `requireUser` authentifie seulement (`services/api/src/plugins/authentication.ts:94`). Liste filtrée par `threadId` seul (`services/api/src/routes/v1/checkpoints.ts:60`), capture et restauration utilisant le `cwd` client (`:103`, `:150`). `assertSafePath` (`:18`) est une liste noire lexicale, sans racine attribuée ni contrôle de propriétaire. Le manager résout les chemins et exécute Git (`packages/vcs/src/checkpoints/checkpoint-manager.ts:54`, `:62`).

Impact possible pour un compte connecté : accéder ou agir sur un dépôt accessible au processus API en dehors de son espace légitime. Le risque dépend des droits du compte système et des chemins connus. Aucun rollback ni accès croisé à des données réelles n'a été tenté. Remplacer les chemins libres par une référence de workspace autorisée côté serveur ; résoudre les liens symboliques avant contrôle ; appliquer ownership sur toutes les opérations et tester deux comptes. Le lien conversation/checkpoint est une question distincte, F10.

### F05 — P0 avant équipes / P1 personnel : reprise globale accessible à tout utilisateur

`services/api/src/routes/v1/pause.ts:40` accepte pause **et reprise** sous `requireUser`, sans rôle supplémentaire. `pause.ts:58` modifie le commutateur global. Ce choix peut convenir à une instance mono-personne ; il ne convient pas automatiquement à plusieurs membres. Définir qui peut arrêter, qui peut reprendre et quelle portée est affectée. La pause ne doit pas être vendue comme annulation instantanée d'une commande extérieure déjà partie.

### F06 — P1 bloquant le parcours principal : arrêt, suivi et reprise divergent

`apps/dashboard/src/lib/conversations.ts:333` efface seulement le suivi ; `:326` le fait aussi après erreur de polling. L'utilisateur peut libérer son compositeur alors que le serveur travaille encore. Le contrat d'annulation est déjà conçu dans Cadran mais non livré. Implémenter une commande serveur idempotente et un état « annulation demandée », conserver l'identité de mission après coupure, puis réconcilier sans nouvelle soumission. Vérifier arrêt pendant un appel, attente d'accord, retry et redémarrage.

### F07 — P1 : accords généraux non intégrés dans le chat web

API de confirmation réelle (`services/api/src/routes/v1/tasks.ts:385`, `:472`), mais DashboardApi n'a pas les wrappers généraux correspondants ; ses méthodes carrière (`apps/dashboard/src/lib/api.ts:1625`) ne les remplacent pas. Le document UX le reconnaît (`docs/design/02-ux-architecture.md:518`). Raccorder accord/refus/expiration à la mission et au run, afficher action, cible et conséquence. L'accord permanent de mission est un changement de sécurité séparé ; il doit rester absent tant que sa portée/révocation n'est pas éprouvée.

### F08 — P1 : intégrations annoncées par leur code mais indisponibles comme outils agent

Recherche des quatre factories hors tests et `dist` : définitions et commentaire d'intégration, aucun appel trouvé. Le registre de domaines contient OSINT et Home (`services/api/src/services/tool-registration.ts:44`). Documents, Google Workspace, Activepieces et outils génériques devices demandent câblage, permissions, configuration et recette complète. Le laboratoire carrière raccorde `RecordingSubmissionAdapter` par défaut (`container.ts:893`), qui ne fait qu'enregistrer (`submission-adapter.ts:77`). Afficher « préparé/enregistré, non envoyé », jamais une preuve de dépôt externe.

### F09 — P1 : estimation de coût sans provenance assez précise

`PricingCatalog` rapproche les noms de modèles (`packages/agent-core/src/usage/pricing-catalog.ts:256`) et retourne un coût générique pour l'inconnu (`:269`). L'API publie un nombre arrondi (`services/api/src/routes/v1/usage.ts:12`), même lorsque le schéma permet null. Il faut distinguer tarif exact versionné, approximation de famille, hypothèse générique et indisponibilité, puis facture réelle. Tester un modèle inconnu et un abonnement sans facturation au token. Aucun prix actuel n'a été vérifié auprès des fournisseurs dans cet audit.

### F10 — P1 : checkpoint de fichier et résultat de conversation sans lien fiable

L'écran initialise `threadId` à `default` (`apps/dashboard/src/ui/sections/vcs-worktrees.tsx:31`) et annonce des checkpoints automatiques (`:541`). La conversation n'impose pas de relation canonique. Cadran propose d'afficher un diff seulement si le thread correspond à la conversation ; ce repli est honnête, mais ne crée pas la traçabilité. Introduire un lien persistant conversation → mission → run → workspace → checkpoint ; marquer explicitement absence de capture et échec de sauvegarde. Le manager masque certaines erreurs de persistance (`packages/vcs/src/checkpoints/checkpoint-manager.ts:123`), à rendre observables.

### F11 — P1 pour domotique durable : commandes satellites volatiles

`services/api/src/services/satellite-service.ts:66` stocke commandes, résultats et états dans des Maps. L'enrôlement persistant ne rend pas la file durable. Après redémarrage, le système ne peut pas garantir le statut d'une commande livrée ni prévenir tous les doubles effets. Persister intention/ack/résultat ; distinguer « résultat inconnu » et « échec ». Ne pas répéter automatiquement une action physique dont l'effet est incertain.

### F12 — P0 si bootstrap exposé : premier administrateur non atomique

`services/api/src/services/persistence/prisma-user-store.ts:12` compte puis crée ; `services/api/src/routes/v1/auth.ts:58` expose l'inscription. Deux inscriptions simultanées peuvent voir zéro. Risque statique non reproduit en PostgreSQL. Initialisation verrouillée à usage unique et politique explicite d'inscription après bootstrap ; pas d'affirmation d'attaque distante sur une instance loopback déjà initialisée.

### F13 — P1 : sauvegarde et mise à jour mal expliquées

Le guide `docs/operations/updating.md:19` annonce une commande `backup create --output` et l'inclusion des secrets. Le parseur effectif (`packages/cli/src/index.ts:206`) utilise `backup [options]`, ne traite pas `create/--output` et n'inclut les secrets que sur option. `backup.ts:103` autorise leur inclusion sans chiffrement en avertissant seulement. L'export navigateur ne contient pas les bases (`Settings.tsx:1109`). Une personne peut donc croire disposer d'une sauvegarde plus complète qu'elle ne l'est.

Corriger les guides à partir des commandes testées ; afficher le contenu, exclusions, chiffrement, dernière vérification de restauration et récupération du coffre. Évaluer aussi la couverture de la DB Mission Engine en mode PostgreSQL : le chemin explicite actuel sauvegarde le SQLite du moteur (`backup.ts:77`), pas une preuve de couverture de tous les profils HA.

### F14 — P1 : fin de vie des données et récupération de compte incomplètes

Les suppressions unitaires de conversations et mémoire existent, mais aucun parcours unifié d'export personnel complet, fermeture de compte, révocation de toutes ses délégations et traitement des copies n'a été trouvé dans les routes inspectées. Le guide de désinstallation est infrastructurel (`docs/operations/uninstallation.md:7`). Définir une politique de rétention, les exclusions d'export et les copies externes ; ne pas promettre un effacement tiers instantané. Prévoir récupération locale sûre et révocation des sessions sans modification manuelle de DB.

### F15 — P1 : preuve de qualité trop facile à confondre avec une recette réelle

Le harness API remplace DB/Redis et frontières externes (`services/api/test/harness.ts:19`). Les tests PostgreSQL ont une configuration séparée (`services/api/vitest.config.ts:8`). Le corpus mémoire exclut le modèle réel (`packages/memory/vitest.config.ts:6`). Les suites passent, mais ne garantissent pas abonnement, OAuth, microphone, appareils ni HA. La CI tolère les alertes élevées de dépendances (`.github/workflows/ci.yml:574`, `:578`) : examiner l'atteignabilité et les exceptions, sans réutiliser un décompte daté.

### F16 — P1 livraison / P2 finition : Cadran intermédiaire, documentation contradictoire

La direction visuelle est cohérente : un shell, quatre régions, états lisibles, accords en phrases complètes, focus et zoom spécifiés. Son état réel reste une fondation sur les anciens écrans (`docs/design/03-design-system.md:634`). Contrastes des tokens ≠ conformité de tous les écrans ; la spec signale encore des couleurs fixes dans Career/Trading. Le README annonce une installation sans multi-tenancy (`README.md:32`), alors que routes et schéma d'organisations existent. Les guides mobile et release contiennent aussi des états et commandes anciens. Publier une seule matrice de support par version et éviter de livrer la fondation graphique comme refonte achevée.
